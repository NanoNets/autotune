### G22: why the MFU bar fails while the throughput reproduces

| | exp 22 (2026-09-21) | re-measure (e6ba837) |
|---|---|---|
| mean step time | 0.4444s | 0.4476s (+0.7%) |
| samples/s | 36.01 | 35.74 |
| measured peak | 236.4 TFLOP/s | 230.5 TFLOP/s (-2.5%) |
| tokens per step in the MFU numerator | 2,422 | 1,850 |
| MFU | 33% (median-based); 26% recomputed on the mean | 20.2% |

The workload reproduces to under 1%. The MFU gap is the token count. The new code counts tokens per
step over the timed clean window only: 7 whole passes over the 992 head rows. The old runner averaged
tokens over every step it ran, warmup and profiled step included, with a window of 6.45 passes. The
saved data isn't enough to reconstruct exactly how that reached 2,422, so the old figure's cause is
unconfirmed. The new figure keeps tokens and time on the same steps, as the axiom requires.
GPU-active isn't comparable, by design: 0.771 describes the median-length reference batch
(`[16, 88]`), and exp 22's 93% described its own profiled step.

## Calibration of the invalid tolerance (e6ba837's predecessor, 17b4745)

The reference batch was run 10x untraced and 5x traced in one process, and GPU-active computed for all
50 traced/untraced pairings per config.

| config | ref-batch wall cv | GPU-active min / mean / max | sd | mean + 3 sd |
|---|---|---|---|---|
| SmolLM champion (compile, mb16) | 0.21% | 0.969 / 0.973 / 0.977 | 0.0021 | 0.979 |
| SmolLM static baseline (mb1, max_length) | 0.04% | 0.965 / 0.985 / 0.996 | 0.0107 | 1.017 |
| Qwen champion (fla, mb16) | 0.70% | 0.798 / 0.811 / 0.817 | 0.0057 | 0.828 |

No healthy pairing exceeded 1.0. The tolerance was set to 2% (from a 5% judgement call). The most
saturated config's 3-sd bound, 1.017, leaves 0.3% of headroom: revisit at triage if healthy saturated
probes get flagged invalid. MFU's side of the tolerance is not calibrated (probes read 43-54%).

## Findings outside the checks

1. **An empty trace read as 0% GPU-active.** The ceiling trial's trace recorded no kernels at
   38.97/39.5GB reserved, on pre-PR code too. Fixed in `17b4745` to read as unknown. Cause unverified;
   likely the profiler failing to allocate its buffers near the card's limit.
2. **Qwen's 30-step window isn't at steady state.** 15.67 samples/s at 62 steps vs 33.68 at 186, with
   median/mean 0.33 vs 0.70, on the same rows and the same reference. Most likely `fla`'s Triton
   autotune compiling per new batch width. The "warmup removes one-time costs" assumption fails for
   this stack. Proposed, not built: warm up for one full pass when `steps_per_pass` is known.
3. **The head scan understated wikitext's row lengths ~10x.** Pool p50 92 tokens (SmolLM tokenizer)
   vs the 9 that both earlier runs planned from.
